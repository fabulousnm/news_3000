# 提示词生成技术说明

> 本文档说明 `news_rumor_prompts_3000` 的生成模板、所用模型与生成思路。
> 面向审阅者与后续维护者，不涉及外部方法借鉴。

---

## 1. 生成思路概述

### 1.1 核心问题

本数据集要解决的不是"生成好看的图"，而是**生成可以用来做检测实验的图**。这两者的差别决定了整套设计的取舍：

| 普通文生图任务 | 本数据集的任务 |
|---|---|
| 追求画面美观、语义合理 | 追求**文字精确**、**版式可信** |
| 文字可以由模型自由发挥 | 文字必须**逐字给定**，且**有真值可比对** |
| 不需要配对样本 | 必须有**仅关键文字不同**的成对样本 |
| 可以丢弃失败样本 | 质量分级必须**全部保留** |

因此本数据集**不采用**"给一段自然语言描述让模型自由生成"的常规做法，而是采用**规格先行（spec-first）**的流程。

### 1.2 规格先行流程

```
  冻结配置                    内容装配                    变体派生                 提示词拼装
┌──────────────┐        ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
│ 配额 / 档位   │        │  版面模板     │        │  clean       │        │  分区化自然   │
│ 阈值 / 约束   │───────►│  语句库       │───────►│  subtle      │───────►│  语言提示词   │
│              │        │  虚构主体库   │        │  strong      │        │              │
└──────────────┘        └──────────────┘        └──────────────┘        └──────────────┘
     生成前冻结            结构化内容规格          字段级差异记录          自包含可投喂文本
     (哈希留档)          (文字级真值来源)        (tampering 标注)       (含负向约束)
```

**三个关键设计决定：**

1. **先定版式，再填文字，最后拼提示词** —— 版式与内容解耦后，同一版式 × 不同内容 × 不同模型可以自由交叉，这是消融实验的基础。
2. **文字真值在生成之前就确定了** —— 因为"这张图应该出现什么字"是我们给定的，而不是模型发挥的，所以出图后才能算出实体命中率、错字数、遗漏实体。
3. **异常只改文字字段，不改版式** —— 三档样本共享同一版式，差异集中在文字，才构成有效的成对比较。

### 1.3 与常规做法的关键区别

**① 异常必须在视觉上正常。**
提示词中显式要求模型"不得自动纠正、补全或统一，不得用颜色、圈注、箭头、放大、删除线或任何警示标记突出"。若异常文字在视觉上被突出，检测器会学到"找标记"而不是"找生成痕迹"。

**② 提示词含明确的负向约束段。**
每段提示词末尾都有统一的约束，规定：文字必须可辨认、不得用乱码或占位符替代、不得擅自改写数字、除指定文字外不得添加可读文字、小字不得小于画面高度的 1.2%。

**③ 全套流程确定性可复现。**
随机源由字符串键派生（`sha256(键) → 种子`），不依赖调用顺序。同一份配置必然产出同一份数据，CI 每次提交都会重新生成并比对。

## 2. 提示词生成模板

### 2.1 提示词的段落结构

每条提示词由 **13 个段落**按固定顺序拼装（中文版）：

| # | 段落 | 作用 | 典型长度 |
|---|---|---|---|
| 1 | 画幅与载体 | 指定比例、载体类型、拍摄质感 | 51 |
| 2 | 视觉风格与版面结构 | 界面风格描述 + 分区顺序（`→` 连接） | 128 |
| 3 | 主体与虚构声明 | 发布方、话题、地区、"均为虚构"声明 | 62 |
| 4–10 | **分区内容块** | `【分区】「逐字文字」…` —— 本数据集的核心 | 10–116 / 段 |
| 11 | 真实感细节 | 文字锐利度、字号层级 | 52 |
| 12 | 文字呈现约定 | 逐字呈现、禁占位符、禁改写、小字下限 | 201 |
| 13 | 版面保真与表格要求 | 分区顺序、表格规范 | 56 |

其中**第 4–10 段数量不固定**，取决于该版面模板声明了多少个分区（实测 15–28 个文字槽位，对应 6–11 个分区块）。

每个分区内的每一项都**带字段名**，让模型明确知道该数值代表什么：

```
【互动栏】评论数「154」、转发数「647」、点赞数「8011」。
【时间与来源】发布时间「2025年10月7日 01:10」、核实单位「核实单位：碧江消费者权益保护中心」。
【正文续区】正文第二段「涉及收费的项目均按照公示的收费标准执行……」、正文第三段「线上办理遇到系统故障的，可改约窗口时段办理。」。
```

> **两个已修复的缺陷**（v1.5）：
> ① 角色到分区的解析原先走全局索引，而同一角色在不同版面可属不同分区，
> 冲突时「最后遍历到的版面」胜出，导致点赞数、发布时间等被塞进无关的正文区。
> 现已改为**仅在本版面声明的分区内解析**。
> ② 渲染时只输出「值」不输出字段名，`【互动栏】「647」` 无法判断是点赞还是评论。
> 现已为 300 余个角色建立中文标签表。

### 2.2 分区内容块格式

这是本数据集最关键的设计：

```
【正文续区】「临江市水利局已启动应急响应机制，并派出工作组赶赴现场…」、「本说明由发布单位负责解释，与上位文件不一致时以上位文件为准。」。
【互动栏】「749」、「8198」。
```

**约定（在提示词末尾显式声明）：**
- `「」` 内的内容 = **必须逐字呈现**的文字（符号本身不要画出）
- `【】` = 版面分区名
- `｜` = 表格的列分隔符（用于表格类内容）

**为什么用这套约定：**
- 与自然语言描述相比，**消除了歧义**——"图中有标题和日期"不如"【标题区】「某某通告」"精确
- **机器可解析**——`【】` 与 `「」` 都是可正则提取的结构
- **与真值字段一一对应**——每个 `「」` 内容同时写入 `fields[].value` 和 `visible_text`，出图后可直接与 OCR 结果做集合比对

### 2.3 三档变体如何生成

三档**不是**三份独立提示词，而是**同一份内容规格派生出三套字段值**：

```
基础字段集（clean）
   │
   ├─ clean  ：原样输出，无改动
   ├─ subtle ：应用 2 个「轻度变更算子」
   └─ strong ：应用 3 个「明显变更算子」
```

**变更算子的实现方式**：改动作用于**字段值**，不作用于版式描述。因此三档提示词的第 1、2、3、11、12、13 段完全一致，差异只出现在第 4–10 段（分区内容块）。

**算子示例**（`src/variants.py`，共 12 个）：

| 算子 | 作用的字段角色 | 产生的内容类型 | 产生的规则违反 |
|---|---|---|---|
| `timestamp_shift` | `publish_time` / `post_time` / … | `timestamp` | `date_order` |
| `metric_inflate` | `metric` / `like_metric` / … | `metric` | `number_relation` |
| `headline_conflict` | `headline` / `lead_headline` / … | `headline_body_conflict` | `subject_agreement` |
| `magnitude_boost` | `body_1` / `body_text` / … | `magnitude` | `number_relation` |
| `urgency_insert` | `hashtags` / `topic_tag` / … | `urgency` + `sensitive_addition` | `fixed_text` |
| `official_fabricate` | `attribution` / `editor_note` / … | `official_statement` | `attribution_chain` |
| `omission_cut` | `body_2` / `paragraph2` / … | `omission` | `temporal_window` |
| …（共 12 个） |

**每个算子声明多个候选字段角色，取该版面实际存在的第一个。** 这样不同版面（槽位各异）都能产出完整的三档，不会因为某个版面没有 `publish_time` 字段而退档。

### 2.4 档位由可计算量定义

档位**不用主观"明显程度"判断**，而用三个计数定义：

| variant | `changed_field_count` | `rule_failure_count` |
|---|---:|---:|
| `clean` | 0 | 0 |
| `subtle` | 1–2 | 1–2 |
| `strong` | ≥2 | ≥2 |

连带失败单列于 `collateral_failure_count`，不计入 `rule_failure_count`——避免"改一处导致三处崩"被误算成三处独立异常。

这套定义由 CI 在每次提交时校验（`variant_tier_definition`），实测 3000 条全部通过。

### 2.5 版面模板的抽象层次

31 个版面模板，每个声明**分区顺序**与**每区的文字角色**：

```json
"cn_social_image_post": {
  "platform_family": "cn_social",
  "aspect_ratio": "4:5",
  "sections": [
    {"role": "top_bar",    "pct": 6,  "text_roles": ["platform_label"]},
    {"role": "author_block","pct": 10, "text_roles": ["account_name", "account_meta"]},
    {"role": "body",       "pct": 14, "text_roles": ["body_text", "hashtags"]},
    {"role": "media",      "pct": 54, "text_roles": []},
    {"role": "interaction_bar", "pct": 9, "text_roles": ["comment_metric", ...]},
    {"role": "timestamp",  "pct": 7,  "text_roles": ["publish_time", "source_label"]}
  ]
}
```

**关键机制：角色 → 分区的映射是自动推导的**（`section_for_role()` 遍历全部模板建立索引），而非手工维护字典。这一点很重要——早期版本用手工字典，新增槽位没登记就全部回退到版面首个分区，导致「顶部栏」里塞满正文长句，版式不合理。

### 2.6 内容装配

`src/content.py`（1052 行）按版面声明的每一个 `text_role` 逐一填充内容：

- **语句库**（`src/sentences.py`）：9 个危害主题 × 3 种语言 × 每主题 10 条**互不重复**的完整语句，共 270 条。中文平均 32 字，英文平均 74 字符。
- **虚构主体库**（`config/fiction_library.json`）：按 7 个地区分组的虚构机构、媒体、人名、地名。
- **续句池**：当槽位数超过语句库条目时，使用独立的 20 条续句补足，**不重复语句**。

**文字密度**：由 `visible_text` 实测字符数判定（测量值，非人工设定）。实测中位 271 字符，High 密度 891/1000，无 Low 样本。

## 3. 所用模型

### 3.1 生成侧（提示词产出）

**本数据集的提示词由程序生成，未使用大语言模型。**

这是刻意的设计选择，理由如下：

| 维度 | 程序化生成（本方案） | 大模型扩写 |
|---|---|---|
| 文字真值 | **逐字确定**，可精确比对 | 扩写会引入改写，真值不精确 |
| 可复现性 | 同种子必然同结果 | 采样有随机性，难以逐字复现 |
| 配额控制 | 可精确保证冻结配额 | 需额外校验与回补 |
| 成本 | 零 API 成本 | 3000 次调用有成本 |
| 内容多样性 | 受限于内容库规模 | 理论上更高 |

**核心权衡**：本数据集的第一目标是"文字级真值"，而**逐字确定性**优先于表达多样性。大模型扩写会削弱"这张图应该出现什么字"的精确性，进而使实体命中率等后置指标失去意义。

> 需要说明的是：**扩写并非不可用，而是与本数据集的核心目标冲突**。若未来需要提升表达多样性，可行路径是扩充 `src/sentences.py` 的语句库，而非引入 LLM 改写。

### 3.2 消费侧（图像生成）

数据集本身**不含生成图像**。提示词设计面向以下文生图模型（按项目规划）：

| 模型 | 说明 |
|---|---|
| GPT Image 2 / 2.5 | 当前文字渲染能力最强的一档，作为主力 |
| Qwen-Image | 开源中文文字渲染代表 |
| Nano Banana | 多模态编辑方向 |
| Seedream | 国产主流 |
| FLUX 2.0 | 开源生态 |
| Stable Diffusion | 基线对照 |
| Midjourney | 美学强但文字弱，作为对照 |

**多模型覆盖的目的不是"生成更多图"，而是支撑跨生成器泛化实验**——同一份提示词在不同模型上的文字渲染质量差异，本身就是可分析的对象。

**已知的模型侧约束（影响使用方式）：**

1. **画幅必须在 API 层单独设置**。提示词中的比例是文字描述，实际生效的是 API 参数，两者必须一致。
2. **文字密集，须用最高质量档**。89% 为 High 密度（中位 271 字符），质量档过低会导致文字不可辨认，样本直接判 C/D 级。
3. **模型版本须记录快照**（带发布日期的 ID），跨版本混合会破坏结果可比性。
4. **部分模型不支持 Batch 接口**，须逐条调用。

### 3.3 后置处理（出图后）

数据集 schema 预留了 8 个实测字段，须在出图并完成 OCR 后填写：

`ocr_text` / `ocr_line_boxes` / `entity_hit_rate` / `char_error_count` / `missing_entities` / `extra_text` / `quality_grade` / `text_mask`

**分级阈值在生成前冻结并计算哈希**（记录于 `release_manifest.json` 的 `frozen_quality_threshold_sha256`）：

| 等级 | 定义 |
|---|---|
| A | 命中率 100%、零错字、无多余文字、文内数字自洽、无明显版式异常 |
| B | 命中率 ≥90%、错字 ≤2、无数字一致性错误 |
| C | 命中率 50–90%，或存在数字一致性错误，或存在明显版式异常 |
| D | 命中率 <50%，或大面积乱码，或版面崩塌 |

**全部等级样本均保留，不因分级结果删除样本。** 看到结果后调整阈值 = 全部结论作废。

## 4. 工程实现

| 模块 | 行数 | 职责 |
|---|---:|---|
| `src/common.py` | 218 | 配置加载、配额计划、确定性随机源、文字规格原语 |
| `src/sentences.py` | 391 | 语句库（9 主题 × 3 语言 × 10 条 + 标题变体 + 短标签） |
| `src/content.py` | 1052 | 按版面角色装配内容（中/英双分支） |
| `src/variants.py` | 262 | 12 个变更算子，三档派生 |
| `src/render.py` | 486 | 提示词拼装（分区渲染、角色映射、中英双版） |
| `src/generate.py` | 318 | 入口、校验、QA 报告 |
| `src/export_txt.py` | 179 | 纯文本导出（支持按比例放大到 30000 条） |
| `src/verify_saved.py` | 118 | 发布完整性校验 |
| **合计** | **3024** | |

**质量保障：**
- 生成期 5 项检查（三联完整性、档位定义、组内一致性、禁用词、划分原子性）
- 13 项独立一致性测试（`tests/test_release_consistency.py`）
- 完整性校验（文件哈希 + 冻结阈值哈希）
- CI 每次提交重新生成并比对，**防止事后调整配额或阈值**
